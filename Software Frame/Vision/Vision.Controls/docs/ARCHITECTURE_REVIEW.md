# Vision 多后端编辑器：架构审查与改造边界

> 当前执行顺序、阶段门禁和执行后联网对比要求，以 [IMPLEMENTATION_PLAN.md](IMPLEMENTATION_PLAN.md) 为准。V1.15目标为：保留全部Tools/AI后端，新增Vision.FlowNode，Workbench直接复用通用FlowEditor和Vision.Controls，不新建Vision.FlowEditor。本文保留历史审查事实，不代表该目标已经实现。

## 1. 本轮性质与结论

本轮是源码审查和公开资料对照，只新增本记录，不修改产品代码、算法、工程格式、坐标语义或 SDK 生命周期。不是一次已完成的 VisionPro 产品改造，也不是完整逐文件审计。

结论：现有 Core / Tools / Controls / Workbench 分层有可复用基础，不能推倒重写。主要缺口不是再换一次显示控件，而是**持久工具实例、可被流程复用的执行边界、定位坐标上下文和结果呈现扩展点**尚未形成一条主链。

当前浏览器作为“单工具调试器”是合理的；它与“可保存多个工具实例、连接输入输出并执行任务”的产品工作台不是同一种产品模型。以下相关发现是相对于本次目标的缺口，不将原本的单工具设计直接判为运行错误。

“反射变化”尚待确认：可能指参数反射生成 UI，也可能指仿射变换、定位跟随，或者几何镜像。这三件事不能互相代替，更不能在未确认时统一改变全部工具的坐标语义。

## 4. 主要发现

### F1：当前工程是单工具工程，不是多工具任务（目标缺口，优先级高）

- **证据**：`Vision.Controls/Models/Projects/VisionWorkbenchProject.cs:11` 仅存一个 `Tool`；`Services/Browser/VisionBrowserWorkspace.cs:78` 的 `SelectEntry` 在创建下一工具前释放 `CurrentCard`（91、99 行）。
- **来源**：将“从工具箱选择一种工具调试”作为工作空间的核心操作。
- **后果**：无法仅靠修改 XAML 实现多个同类工具实例、定位结果供下游消费、任务级保存和执行。切换类型不等于选择一个已存在的任务实例。
- **修复方向**：保留单工具编辑器作为可嵌入编辑器。任务组织先核查现有 FlowEditor / FlowNodes 可复用能力；不要另写一套视觉图执行器。工具箱负责添加，任务列表负责选择实例，两种操作必须区分。旧单工具工程继续按旧格式读取；任务级持久化是独立设计和兼容工作，不能偷偷塞入当前清单。
- **依据**：信息隐藏、单一职责；先识别真实产品模型，再设计界面。

### F2：多后端执行与旧流程节点仍是两条边界（扩展风险）

- **证据**：`Vision.Controls/Contracts/IExecutableTool.cs:11–24` 提供图像、校验、执行及可选能力；Core 另有 `ITool` / `IEditableTool`。`Software Frame/FlowNodes/FlowNodes/Vision/SingleTool/Definition/VisionToolNodeBase.cs:32,56` 仍约束 `HalconToolSession`、使用 `HObject`。
- **来源**：旧流程先以 HALCON 会话建设，新编辑器通过 Controls 适配器容纳三个后端。
- **后果**：编辑器能运行 OpenCV / AI，不代表流程节点自动支持这些工具。若流程反过来依赖 Controls，会将无界面运行绑定到 WPF。
- **修复方向**：先核对三个现有契约的使用和生命周期，再收口可复用的非 UI 执行部分；不直接添加第四套同义接口。编辑、对话框和绑定留在 Controls，后端资源继续由创建方持有。旧 HALCON 节点按兼容入口处理，不一次替换全部节点。
- **依据**：依赖倒置、端口与适配器；复用执行能力不等于复用视图层。

### F3：坐标能力存在，但没有贯穿当前主执行链（功能缺口）

- **证据**：Core 已有 `CoordinateChain`；两个后端有 `Coordinate/ResultCoordinates.cs`；ROI 编辑器有 `FollowFixture`。本轮在 Vision 源码内搜索这些调用，结果转换和编辑器跟随的调用主要出现在测试，主编辑执行契约仍以 `Run(VisionImage?)` 为入口。
- **来源**：坐标算法、结果转换帮助类和编辑会话分别建设，缺少明确的运行时坐标上下文与绑定策略。
- **后果**：不能把“有仿射类”说成“所有工具已支持定位跟随”；不能把世界坐标结果直接画回原图，也不能重复修改 ROI 造成累计漂移。
- **修复方向**：待确认需求后，复用已有矩阵和坐标链，明确基准姿态、当前姿态、图像坐标、结果坐标与单位。保留基准 ROI，由本次运行快照推导执行 ROI；原始结果保留像素语义，显示和对外坐标转换明确区分。
- **边界**：`Pose2D` 只表示平移与旋转，不是完整仿射。非均匀缩放或错切会把圆变成椭圆、旋转矩形变成平行四边形；不能把不能表达的变换悄悄塞回原 ROI。卡尺长度、梯度方向和测量单位也需要逐项定义。
- **依据**：显式领域语义、避免隐藏状态与重复转换。

### F4：新增结果类型需要同步修改多个中心分支（扩展风险）

- **证据**：`Presentation/Rendering/VisionDisplay.cs:38,46,64`、`Presentation/Results/VisionResultTable.cs:34`、`Views/Imaging/VisionImageViewport.cs:417–476` 分别识别具体算法结果类型。
- **来源**：将少量已知工具的结果映射集中在共享帮助类和画布中。
- **后果**：第三方结果要进入图像、表格和摘要时，容易发生一处支持、另一处遗漏；通用画布继续感知更多算法类型。
- **修复方向**：先沿用 `VisionResultItem`、结果表和选择模型，把一个现有结果类型的呈现转换收口验证；确有第三方接入需求时，在装配处注册对应呈现适配。画布最终消费几何、标签和选择标识，而非判断工具名字。保留原始结果与后端独有字段，不把所有结果压成一个巨大 DTO。
- **非目标**：不是为了消灭 switch 或 DataTemplate 而改写所有展示；异构结果模板本身有必要。
- **依据**：开放封闭、变化点隔离；扩展点要服务实际接入，而非预先建设插件框架。

### F5：显示画布承担结果识别与专用编辑协作（维护风险）

- **证据**：`VisionImageViewport` 既负责视口绘制/交互，又直接识别 Blob、检测、模板、两个后端找线结果；同时通过 partial 文件承担 ROI 与找线编辑。
- **来源**：交互逐步叠加在共享画布上；拆为 partial 改善了文件浏览，但没有改变职责边界。
- **后果**：添加一种工具的专用图形，可能影响通用图像交互、选择和截图行为。
- **修复方向**：先处理 F4 的结果输入边界，再按实际修改需要提取已有几何绘制/命中测试的纯逻辑；保留当前交互会话、取消、鼠标捕获和单一视口。不要立即引入图层引擎、调度器或通用交互框架。
- **依据**：高内聚、降低变化传播；行数本身不是拆分类的理由。

### F6：注释数量多，但有不少缺少领域信息（改进建议）

- **证据**：例如 `VisionBrowserWorkspace` 和 `ResultCoordinates` 中“正文中的关键协作调用包括……”等注释，只复述调用名称。
- **后果**：真正重要的坐标方向、单位、所有权、跳过图外卡尺的原因、取消边界被模板化文字淹没。
- **修复方向**：随实际修改替换相关注释，解释输入输出、单位、坐标系、原生资源所有者、失败和取消策略。保留必要 API 文档，不做无关的全仓注释重写。

## 5. 推荐的 Workbench 呈现

```text
任务级：新建 / 打开 / 保存 / 执行当前工具 / 执行任务
┌────────────────┬───────────────────────────┬──────────────────┐
│ 任务工具实例    │ 打开图像/导入图像/保存图像 │ 参数 | ROI | 结果 │
│ 定位 → 检测…   │ 原图 | ROI | 训练图 | 结果 │ 能力专用附加内容 │
│ 添加工具箱     │                           │                  │
│ 后端/类别筛选  │ 自定义图像画布            │                  │
├────────────────┴───────────────────────────┴──────────────────┤
│ 当前执行状态 / 耗时 / 校验错误 / 本次结果摘要                  │
└──────────────────────────────────────────────────────────────┘
```

- 上图是目标，不代表当前已有任务执行功能。没有实现前不添加占位“执行任务”按钮。
- 任务级打开/保存与图像级打开/保存必须明确命名、所有者和取消语义；不能出现两个看似相同却保存不同内容的按钮。
- 图像操作栏仍直接声明固定按钮和视图切换，不重新生成一套动态按钮框架。
- “保存图像”保留原像素语义；若另需保存视口，应独立命名，不能把截图当原图。
- 参数页用属性元数据自动生成普通参数。ROI、训练模型交互和复杂结果表不是普通标量属性，允许复用专用组件。
- 参数 / ROI / 结果是基础页；训练、AI 模型准备等按已声明能力呈现，不逐工具复制整个编辑页面。
- 后端可以作为工具箱筛选和实例信息，不应成为三套重复的工作台。
- 暂不引入 Docking 依赖、复杂布局持久化或大批新视图。

## 6. 形状匹配与灰度匹配的实际边界

已有两条可复用实现：

| 类别 | 当前实现证据 | 不应作出的承诺 |
|---|---|---|
| 灰度模板匹配 | `Tools/OpenCv/Matching/TemplateMatchTool.cs:126` 使用 `Cv2.MatchTemplate`，并有模板编辑能力 | 不能仅靠改名宣称已具备旋转/缩放搜索或 VisionPro 全部能力 |
| 形状匹配 | `Tools/Halcon/Matching/ShapeMatchTool.cs:203` 使用 `FindScaledShapeModel`，并有训练/模型编辑入口 | 需要授权 Runtime；本轮未执行。不能宣称 OpenCV 已拥有相同算子 |

后续按“训练区域/模板原点 → 模型准备 → 搜索参数 → 多匹配选择 → 分数/姿态 → 下游定位”的闭环验收，不另造一套模型编辑器。

若需要灰度匹配旋转/缩放、HALCON NCC 或 OpenCV 形状匹配，应逐项确认算法、精度与运行时间目标；它们是实际算法工作，不是给 UI 增加几个参数。不同后端不要求都有同名工具或相同数值阈值。

AI 继续沿用 `IAIProvider` 和已有模型准备能力。分类、检测、分割、异常检测保留各自结果语义；不把“加载推理模型”称为“训练模型”。

| 注释清晰 | 存在模板化注释 | 随修改写清单位、坐标、生命周期、异常和取消 |

## 8. 建议实施顺序与验收

每阶段独立交付、检查 diff，不把后阶段内容顺手加入前阶段。

### A. 先验证共同执行/呈现边界

- 明确第三方工具如何复用现有执行契约，不依赖 WPF；保持旧入口兼容。
- 选一个现有结果验证图像、表格、摘要、互选都从同一呈现转换获得。
- 复用现有工具箱注册和属性编辑器，不新增项目或插件扫描框架。
- 验收：原工具结果不变；新接入不要求改通用画布；异常、取消、释放及迟到结果隔离有回归。

### B. 定位/坐标跟随（需求确认后）

- 先做平移、旋转、恒等变换的最小闭环；是否支持缩放、错切、镜像分别明确。
- 基准 ROI 不累积改写；本次图像、ROI、坐标上下文和参数保持一致快照。
- 验收：多次执行无漂移；反变换和结果叠加一致；不支持的形状变换明确拒绝；像素与物理单位不混淆。

### C. 匹配闭环

- 复用两类已有工具及训练入口，明确模板原点、角度单位、多匹配、结果选择和模型引用的保存行为。
- 对新增旋转/缩放搜索先建立能失败的合成回归，再实现；不降低现有精度断言。
- 验收：训练/读取失败保旧，工程重开行为明确，原图不变；HALCON 测试保留 Runtime 门槛。真实图像精度另行验收。

### D. 工作台任务组织

- 在核查 FlowEditor / FlowNodes 后决定最小复用方案；工具箱“添加”与任务实例“选择”分离。
- 验收：同类工具多个实例互不覆盖，选择不销毁任务实例，输入输出连接明确，任务保存/恢复兼容策略明确。
- 不以“先做界面”创建不能运行的任务列表和按钮。

### E. 跟随实际变更清理

- 删除前同时核查 C#/XAML、资源 URI、注册、反射、工程标识和兼容契约。
- 保留必要异构模板和共享主题合并层级；不批量改命名或所有注释。
- 使用现有逻辑与 WPF/STA 测试工程；构建不等于 UI 验收，模拟 DPI 不等于真实跨屏，fake 不等于硬件验收。
