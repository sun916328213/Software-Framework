# MachineApp 配方与 SECS 页面：一个数据源，两种职责

## 本轮已实现与未实现

已实现：Workbench 提供强类型配方、示例及“配方管理”列表/手动切换；Controls 已移除 S7 专用联调页签，后台通过 `ConfigureRecipeSource<T>` 校验 S7F3 JSON 并通知宿主列表刷新，绑定时补同步已接收正文（见 [Workbench 说明](../SecsGem.Workbench/README.md)）。通信处理不依赖页面打开，不改变当前 PPID 或当前快照。此应答后的内存集合桥接不是下述生产事务服务。
本轮也已提供 `IFormattedRecipeCodec<T>` 双向编解码扩展点；后续项目通过宿主编解码器定义配方属性、CCODE、PPARM 类型、步骤结构及元数据，不修改 S7F23/S7F25。现有 `ParameterBlockRecipeCodec<T>` 仅为简单参数块适配器，不是全局工艺协议。初始化导入与合法 S7F3 同步会发布格式化快照，使 S7F25 可读取本地业务配方；仍不自动追踪任意字典编辑，不能将此桥接当作生产唯一配方服务。编解码器由宿主创建并借给 Controls，不能在 Encode/Decode 内连接设备或切换当前配方；Dispose 仅清除引用，不代为释放宿主服务。

尚未实现：MachineApp 生产配方服务适配、业务权限、持久化流程、自动配方变更事件和机台当前配方状态。当前 S7 处理器仍使用 Runtime 内存库。
下面是生产接入设计建议，不是已经可注册使用的 API。

## 不要把 App 的配方 ViewModel 传给 Controls

配方所有权属于 MachineApp。Controls 不应知道机型配方实体、数据库表、具体工艺参数或 App 的 ViewModel。
也不建议让 App 和 SECS 各维护一套配方集合再相互同步：这会产生版本漂移，尤其是 Host 下载/删除时。
只给 Controls 设置 ItemsSource 也不够：UI 虽然显示 App 配方，S7 处理器仍可能回复另一份内存库。

推荐依赖关系：

```text
MachineApp 配方编辑页 ───────────────┐
                                    ↓
                       App 配方应用服务（唯一数据源）
                                    ↑
                       App 的 SECS 配方适配器
                                    ↑
                       SecsGem.Core 配方服务契约
                                    ↑
                 SecsGem.Runtime（S7 处理器和状态策略）
                                    ↑
                   SecsGem.Controls（只读诊断投影）
```

Workbench 单独装配内存实现；MachineApp 装配生产适配器。
生产实现缺失或读写失败时明确失败，不能静默回落到演示内存库。
页面是否打开，不应影响 S7 配方服务是否可用。

## 两个 UI 不重复做同一件事

| 项目 | MachineApp 配方页 | SecsGem.Controls 配方页 |
|---|---|---|
| 用户 | 操作员、工艺工程师 | 调试/通信工程师 |
| 内容 | 工艺分组、单位、范围、校验、业务解释 | PPID、协议格式、版本、长度、传输/验证结果 |
| 参数 | 唯一可编辑入口 | 原始报文只读预览，必要时折叠或隐藏 |
| 操作 | 新建、编辑、保存、选择、应用生产配方 | 查看、筛选、刷新、诊断报文 |
| 数据源 | App 配方服务 | 同一服务的已提交只读快照 |

如需从 SECS 页检查业务细节，提供“在配方管理中打开”的宿主导航回调，传递稳定 RecipeId/PPID，
由 MachineApp 导航到已有配方页。不要把另一份编辑器嵌进 SECS 页，更不要共享两个编辑页面的 DataContext。
生产宿主可以按角色隐藏诊断页或原始参数预览；这只是 UI 展示策略，不替代运行时权限校验。

## 建议的 Core 契约职责

后续可在 SecsGem.Core 定义异步配方服务接口（例如 `ISecsProcessProgramProvider`，名字仅为建议），包含：

- 查询已提交的配方目录和版本。
- 按 PPID 读取不可变快照/二进制正文/格式化命令 DTO。
- 检查加载请求和容量、权限、设备状态。
- 校验并提交 Host 下载的数据；返回明确业务结果。
- 按策略删除指定配方或全部配方。

Core DTO 不依赖 WPF、Prism、Secs4Net.Item 或 MachineApp 数据库实体。
二进制与格式化转换在适配边界处理，明确 MDLN/SOFTREV/CCODE/PPARM 的机台映射，不把整个 App 实体默认 JSON 化就声称符合格式化配方规范。
Runtime 将业务结果映射成 PPGNT/ACKC7，并由正常传输返回。

写入接口应支持取消/超时，并由 App 服务定义事务提交点；已提交后不能因超时重试重复副作用。
配方服务属于宿主，Controls 只借用。Runtime 的 Host 请求、UI 查询应走同一个服务，而不是只给 UI 注册服务。

## Host 修改与本地编辑如何共存

1. App 编辑器持有“草稿”，Host 默认读取最后一次成功提交的版本，不读取未保存字段。
2. Host 下载先解码、参数语义校验、权限/运行态检查，再提交；只有实际提交成功后才回复接受。
3. 已接收/已保存不等于已选择/已应用到生产。应用生产配方必须走 App 的安全状态机。
4. Host 与本地同时改同一配方，用修订号/乐观并发或服务内串行化防冲突，不能无提示覆盖未保存草稿。
5. 提交成功后发布应用内变更通知，两个 UI 读取新的同一版本；另按通信规格上报 `S6F11 E→H` 的 PPChange 类采集事件，Host 通过 `S6F12 H→E` 确认。C# 事件/刷新 UI 不等于 Host 已收到 SECS 事件。未保存编辑器提示冲突，不自动覆盖草稿。
6. 禁止删除运行中、已选中或锁定的配方等策略由 App 服务统一裁决，隐藏按钮不能当安全保护。
7. 如果需要审核 Host 配方，明确“接收区/待审核”和“已发布生产配方”的区别，并在双方通信规格中定义可见性与应答语义。

## PPID 与选中配方不是一个概念

- PPID 可由数字组成，但本实现编码为 ASCII 标识；`001001` 与 `1001` 不合并，App 的整数主键需要显式映射。
- Controls 的测试 PPID 和目录选中行不是机台当前配方，变化时不能自动发送 PPChange 或应用事件；模拟宿主只能在 Workbench 手动切换当前配方。
- 修改同一 PPID 的正文、重命名 PPID、选择另一配方分别对应内容变更、目录变更和当前状态切换。
- PPChange 的 CEID/RPTID/VID 以及状态枚举需由双方通信规格确定，不在通用 Controls 中硬编码。
- 重命名应由业务服务原子提交，并按约定通知旧/新 PPID；向内存库写入新 PPID 本身不会删除旧 PPID，不能冒充重命名。
- 真正切换配方时，只有机台应用成功后才更新当前 PPID 状态并上报选择/应用成功事件；失败不能只因下拉框变化而上报成功。
- 事件绑定在业务服务提交点，独立于页面 Loaded/Unloaded；等待 S6F12 不应占住服务锁或阻塞 S7 应答。

## 当前到生产的迁移顺序

1. 本轮用 Workbench 演示数据联调 S7 报文，不涉及 MachineApp。
2. 确认 MachineApp 现有配方保存/读取/选择服务、PPID 映射及双方通信规格。
3. 在 Core 增加最小服务契约，由 MachineApp 实现适配；让 Runtime 的 S7 处理器和 Controls 查询共同使用它。
4. 将 Workbench 内存库作为显式演示实现，不保留生产双写/自动兜底路径。
5. 增加“App 保存→Host 读取”“Host 下载→App 显示”“并发编辑冲突”“运行态拒绝删除”“持久化失败不回复成功”等跨层测试。

这样保留两个入口，但只有一个配方编辑器和一个数据源；SECS 页显示的是通信诊断，不是第二套工艺管理。
