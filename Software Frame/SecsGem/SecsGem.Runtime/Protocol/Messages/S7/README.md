## 修正发现的问题

| 原实现 | 修正 |
|---|---|
| S7F20 用 `L[n] L[2] PPID, PPBODY` 表示目录 | `L[n] PPID`，不泄露正文 |
| S7F23/26 为私有 `L[2] PPID, PPBODY` | `L[4] PPID, MDLN, SOFTREV, L[commands]` |
| S7F25 用 `L[1] PPID` 请求 | 正文直接为 PPID |
| S7F23 收到主消息后尝试解析 S7F24，S7F25 尝试解析 S7F26 | 主请求执行存储/查询，回复解析按实际 F 区分 |
| ACKC7=1/2/3/4 的文字含义错误 | 1 无权限、2 长度错误、3 矩阵溢出、4 PPID 不存在；5 模式不支持、6 稍后执行 |
| 格式化参数向量只保留第一个值，F4/F8 当 byte 读取 | 按真实类型复制全部元素，保留空向量和 B/U1 区别 |
| 畸形回复返回 B(0)，看起来像成功 | 非法结构返回 null，沿既有传输链生成 S9F7，不改库 |

旧的非标准 S7F23 字符串加正文列表调用不再发包。
`S7F23SendData` 保留类型名，继承扩充后的 `ProcessProgramData`；必须提供四字段结构。
接收后的 `PPBODY` 每项是独立复制的 `Item` 命令，不再把类型信息丢失成单个 .NET 标量。
`ProcessProgramInfo.PPBODY` 仅为旧 API 保留，不进入 S7F20。

## 本次支持的常用事务

H=Host，E=Equipment。标准允许方向与本页实现的联调方向不是同一概念：

| 事务 | 标准主消息方向 | 本页请求 / 应答方向 | 主消息正文 | 回复正文 |
|---|---|---|---|---|
| S7F1/2 加载询问 | H↔E | F1 H→E / F2 E→H | `L[2] PPID, LENGTH` | `B[1] PPGNT` |
| S7F3/4 非格式化配方发送 | H↔E | F3 H→E / F4 E→H | `L[2] PPID, B PPBODY` | `B[1] ACKC7` |
| S7F5/6 非格式化配方读取 | H↔E | F5 H→E / F6 E→H | `PPID` | `L[2] PPID, B PPBODY`；未知为 `L[0]` |
| S7F17/18 删除 | H→E | F17 H→E / F18 E→H | `L[n] PPID`；空列表表示全部 | `B[1] ACKC7` |
| S7F19/20 目录 | H→E | F19 H→E / F20 E→H | 无正文，不是 `L[0]` | `L[n] PPID` |
| S7F23/24 格式化配方发送 | H↔E | F23 H→E / F24 E→H | `L[4] PPID, MDLN, SOFTREV, L[commands]` | `B[1] ACKC7` |
| S7F25/26 格式化配方读取 | H↔E | F25 H→E / F26 E→H | `PPID` | 同 S7F23；未知为 `L[0]` |

双向事务的应答总是返回主消息发起方，不能仅凭奇数/偶数 F 推断固定 H/E 方向。
[Controls 后台配方同步](../../../../SecsGem.Controls/README.md) 负责 JSON 转换与宿主通知；专用 S7 联调页签已移除，Host 使用外部模拟器。Workbench 的“配方管理”显示列表并手动切换，下载不自动切换。允许双向不表示本项目已经完成设备主动上传/请求配方的全部业务流程。

PPID 继续沿用非空 ASCII 字符串身份约定，不再由共用转换器固定为最多 120 字符；保持该约定是为兼容目录、查询和 S9 会话标识，不是将数字类型猜成标识符。MDLN/SOFTREV 接受 ASCII/JIS8 文本，取消固定 20 字符与内容字符扫描；接收的两种元数据类型在存储、读取快照和回传时保留，本地新建数据默认使用 ASCII Item。实际编码能否表示某字符取决于 SDK/项目的编码配置，纯内存转换通过不等于线上编码已验收。

以上为项目兼容策略，不代表严格标准限制被修改。需要 120/20 等互通约束的宿主应在项目业务入口执行，不固化为所有配方的通用限制。总消息容量仍由显式接收策略负责，无固定字符上限不等于无限接收。
PPID 是标识符，不是必须为数值的数据项。数字业务编号也应按约定编码，例如 `001001` 为 `<A[6] '001001'>`，不是 `<U4[1] 1001>`；`001001` 与 `1001` 是不同标识，应保留前导零。
MachineApp 可使用整数主键，但应在适配器中显式映射为 PPID，不将数据库主键类型直接用作线上数据类型。
二进制 PPID 未实现，不应宣称覆盖 E5 的全部允许格式。
LENGTH 接收 U1/U2/U4/U8 单元素；超过数组可表示长度回复 PPGNT=2，无服务时为 5。
加载询问不创建空配方、不预留磁盘、不绑定后续传输的业务会话。
格式化命令容器为 `L[2] CCODE Item, L[n] PPARM`。按宿主兼容要求，协议层已移除 CCODE 的 U2 类型和单元素限制，原始类型、元素数量和值均独立复制并在 S7F26 原样回传，不把 ASCII 数字自动改成 U2。这是相对原 U2[1] 契约的兼容扩展，不应据此声称严格标准符合性。外层四字段、命令 L[2]、PPARM 列表及 PPID/元数据校验仍保留。业务含义和可应用性由宿主编解码器校验；简单参数块也允许 ASCII 数字及可转换的数值类型，但仍校验命令含义、参数完整性和目标业务范围，不代表业务限制被取消。
未知删除 ID 回复 ACKC7=4，并保持整批不变；畸形请求走 S9F7。

## S7F23 / S7F25 拒绝原因定位

非法报文仍返回 S9F7，但处理器现在会在 EQ 消息监视器/SEMILog 记录函数名、字段位置及实际类型/数量，例如：

- `S7F23 ... 命令[1].PPARM 要求 L[n]，实际 ASCII[20]`
- `S7F23 ... MDLN 需要文本项（ASCII/JIS8），实际 Binary[0]`
- `S7F25 ... PPID 要求 ASCII，实际 List[1]`

不要仅按 FastSIM 模板树中的名称或 `<nothing>` 推断实际线上类型；排查时提供 EQ 的具体拒绝日志及发出的完整 SML/原始字节。当前不再因 CCODE 为 ASCII/U4/空或多元素而产生原先的 U2[1] 拒绝；其他结构校验不变。

## ProcessProgramCodec 职责

- `ReadFormatted / WriteFormatted`：报文和现有字符串元数据、命令集合之间转换，不判断机型/版本兼容或参数业务含义。
- 共用结构读取仅保证四个字段、命令 L[2] 和 PPARM 列表能够明确定位；元数据仍须是文本项，不猜测 Binary 的字符编码或将数值型号隐式字符串化。
- CCODE 和参数不限定具体类型、业务字段、数量、向量长度或嵌套内容。空元数据和空参数合法；PPID 不得缺失。
- `Copy / Value` 继续保留 Item 的原始格式、全部元素和深层数据；接收对象、存储、读取副本互相独立。
- 取消固定长度策略不取消现有宿主 JSON/业务范围检查；协议存储成功也不表示已可应用。
- 写出失败会释放本次创建的独立 Item 树；DeviceManager 也释放转换用临时树，不释放调用方借用 Item。

## 存储与硬件安全边界

- 这是一套内存配方服务，ACKC7=0 表示已存入当前 DeviceManager，不表示配方已持久化、验证或装载到设备。
- 同 ID 再下载替换对应格式的内存正文；二进制与格式化正文可以分别存在。目录不承诺排序。
- 空删除列表清除两种正文及目录；普通删除完整解析和校验后才修改。
- DeviceManager 由容器创建/持有；处理器只借用，不创建网络连接或额外会话资源。
- 收到的 Item 是传输层借用对象，保存时复制成托管数组 Item；读取时再次复制，避免接收内存回收或调用方修改污染库。
- 协议存储、读取、删除用同一锁协调。旧的 public ConcurrentDictionary 兼容属性仍存在，直接写字典的调用方会绕开这些保证，应使用方法入口。
- 本次未改变 Runtime/Transport 的取消、超时、断连、重连和释放所有权。
- 不自动切换选中配方、不执行配方、不写文件/PLC/设备；权限、运行态禁止删除、选中配方保护、容量限额及持久化仍需机台策略接入。

## 配方修改与事件上报（当前缺口）

当前实现只有 S7 内存读写及其事务应答，**没有自动 PPChange 上报，也没有机台当前选中/执行配方模型**。
S7F4/18/24 的 ACKC7 不能替代设备本地配方变更通知。
典型通知为 `S6F11 E→H`，Host 以 `S6F12 H→E` 确认；CEID/RPTID/VID 数值必须按机台通信规格配置，不能凭模块自行选一个通用数字。

| 操作 | 是否产生业务变更事件 |
|---|---|
| 修改联调页测试 PPID、生成模板、只读选中目录项 | 否，没有提交变更，也没有切换生产配方 |
| 创建、保存修改、删除真实配方 | 成功提交后按 E30/Host 规格产生 PPChange 类事件 |
| 重命名真实 PPID | 作为目录变更；S7 没有通用“修改 PPID”指令，按规格处理旧项删除/新项创建或约定的重命名事件 |
| 机台实际选择/应用另一配方 | 更新当前 PPID 的状态变量，并按规格上报选择/应用成功事件；不等同于正文被修改 |
| 校验失败、保存失败、取消、未保存草稿 | 不上报成功变更 |

PPChange 关联数据通常包含 PPChangeName、PPChangeStatus；具体类型/枚举按采用的 E30 版本和 Host 规格核对。
重命名可以在约定的报告中携带旧 PPID、新 PPID、版本；这些扩展数据需双方约定。
对 Host 发起的修改，变更事件的适用范围和与 S7 应答的先后顺序也需按通信规格落实，不能在回包前同步等待 Host 的 S6F12 导致互相等待。

正确接入点是 MachineApp 配方服务的成功提交点，不是 Controls 属性 setter 或 PropertyChanged。
现有 `SetVariable`/`ReportEventAsync` 可作为后续接入基础，但仍需配置报表关联、启用/订阅状态、事件数据快照、串行化及失败处理。
不能用共享 VID 先写 A 再写 B 的无锁并发流程发送两个事件，否则两条报告可能都携带 B。
断线、事件未启用或通知失败不应回滚已经成功保存的配方，也不能静默声称 Host 已获知；是否持久排队/重放必须单独设计。
Workbench 提供配方类型、示例和“配方管理”；JSON 转换及接收后的列表通知统一在 Controls 后台。专用联调按钮已移除，以上操作目前都不自动发变更事件。
