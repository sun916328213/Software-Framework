# 离线授权模块

## 解决方案与职责

打开仓库根 `Software Frame.sln` 的 **14 Licensing**，或本目录的独立 `Licensing.sln`：

```text
14 Licensing
├─ Licensing.Authorization（授权：厂商签发工具）
├─ Licensing.Activation（激活：客户激活工具）
├─ Licensing.Workbench
├─ 组件
│  ├─ Licensing.Core
│  ├─ Licensing.Trust
│  └─ Licensing.Client
└─ Tests
   ├─ Licensing.Tests
   └─ Licensing.Wpf.Tests
```

没有"开发与验证"分组。必要的脚本保留在磁盘 `Build/`，不在解决方案中铺开显示。修改后若 VS 未刷新，请重新加载解决方案。

- **Licensing.Authorization**（授权）：仅厂商使用，签发、续期、历史记录、验证及签发环境管理；绝不交付客户。
- **Licensing.Activation**（激活）：客户导出 `.sfreq` 申请单（机器码 + 可选的时间恢复请求）、导入 `.lic`（选文件或直接粘贴授权文本）、申请时间恢复；用完即可关闭，不承担常驻监控。
- **Licensing.Workbench**：无设备的 WPF 验证宿主，演示持续检查、提醒、任务入口复查和退出清理，不启动 MachineApp。
- **Licensing.Core**：.NET 9 授权核心，签名、产品、机器、功能及时间校验的唯一实现，厂商工具与客户工具共用。
- **Licensing.Trust**：全仓**唯一**的信任锚，编译期嵌入签发方公钥与产品标识。激活工具、Workbench 以及未来接入的 MachineApp 都引用它，不再各自嵌一份 —— 换身份只需重新生成这一个程序集，也避免出现「两个程序嵌了不同公钥」的漂移。
- **Licensing.Client**：客户端适配层，直接调用 `Licensing.Core`，并提供后台监控与 WPF 会话封装。net9.0 目标只有监控逻辑，net9.0-windows 目标增加 WPF 适配，避免纯逻辑测试依赖 WPF。源代码命名空间 `Licensing.Native.Client`、`Licensing.Wpf` 沿用历史名称（消费者已依赖），输出统一为 `Licensing.Client.dll`。

## 日常授权流程

1. 客户运行供应商提供的完整激活工具，点 **导出申请单** 生成 `.sfreq` 发给厂商。隔离网络、远程桌面或只允许文件传输的场合走这条；同一台机器也可以只复制机器码。
2. 厂商点 **从申请单读取** 自动填入机器码（申请单带时间恢复请求时一并填入），填客户名称和 **天数**（或勾永久/试用），点击 **生成授权文件**。到期时刻为今天起第 N 天的 23:59:59，界面实时显示算出的到期时间。
3. 工具直接生成 `.lic`、自动留档，并在资源管理器定位文件；不再先生成文本再另存。
4. 客户点 **激活**：把授权文本粘贴到输入框后点「激活」，或输入框留空直接点「激活」选择 `.lic`（自动忽略换行、空格、全角空格与 BOM，只做格式粗筛，验签仍由授权核心完成）。有效授权不会要求客户选择其他配置文件。
5. 续期从授权记录选择设备，点击 **选择记录续期**，确认新期限后重新生成；旧记录不覆盖。记录可按客户、机器码、产品筛选。
6. 客户可点 **清除本机授权** 删除本机授权文件；时间记录保留，不退还授权、也不解除机器绑定。

厂商验证页自动使用当前签发身份，按签发页所选产品检查签名和期限，不要求厂商电脑等于客户机器；既可选择 `.lic`，也可直接粘贴客户发来的授权文本。历史记录浏览允许显示当前身份签发的其他产品，但这不代表客户允许跨产品授权。

## 厂商机器与客户机器的分工

| | 厂商机器（工具绝不交付） | 客户机器（只拿到发行包） |
|---|---|---|
| 工具 | **Licensing.Authorization**（授权）：初始化身份、签发、验证、生成客户包 | 发行包里的 **Licensing.Activation**（激活）：导出申请单、导入授权、申请时间恢复 |
| 需要知道的 | 产品标识、身份密码、历史记录 | 什么都不需要 |
| 看不到的 | — | 厂商工具、签发身份、备份、托管授权核心 |

产品标识与公钥在**编译期**嵌入 `Licensing.Trust.dll`（见 `Build/ClientProduct.targets` 与 `Build/Trust.props`），因此客户不需要、也无法选择它们；换身份或换产品必须重新生成客户包，不能靠改配置文件。**所有程序共用这一份定义**，公钥随仓库提交，不需要为每个程序单独填。

源码目录 `bin/Debug` 下的 `Licensing.Activation.exe` 是**开发构建**：公钥已经随 `Build/Trust.props` 一起编进程序集，但产品标识只来自不入库的 `.local/client.props`，所以运行时显示"开发构建 · 缺少产品标识"属正常状态，不是故障。它只用于本机自测或对照排查；生产上这台机器不需要运行它。开发构建下 **导出申请单** 仍然可用（没有产品标识就只写机器码）—— 客户第一件事是把机器码发出来，与能不能激活无关。

## 签发身份：密码加密，随工具文件夹便携

原始公钥/私钥文本不再出现在日常界面。不是每台设备生成一套密钥，也不从公开机器码推导签发凭据。

通过 **签发身份与密码**：

- 首次使用：输入并确认至少 12 字符的密码，明确确认后初始化，生成 RSA 3072 位签发身份。不会在启动或损坏时静默换钥。
- 每次启动：有便携身份时弹出密码解锁窗口；解锁后本次会话可持续签发，不用逐台输入密码。关闭工具会清除会话派生密钥，不把密码保存到磁盘。窗口按身份状态重建内容：未创建时只出现"创建签发身份"，已创建未解锁时只出现"解锁"，已解锁时只出现"创建加密备份"，不再用置灰按钮表达状态。
- 换电脑或 Windows 账户：直接复制完整工具文件夹（包含 `IssuerData/`），输入相同密码即可使用，不需要恢复操作，也不依赖原电脑。
- 已有旧本机身份：在原电脑关闭旧工具，再使用 **迁移原电脑的本机身份（仅一次）**，设置新的便携密码。保留同一签发身份，复制旧授权记录和最近产品设置，原文件不删除。DPAPI 仅用于该一次性旧数据读取，日常签发不再使用它。
- 首次初始化只要求输入并确认密码，不再提供"迁移旧环境文件"入口；历史上以明文私钥文件迁移的路径已移除。
- 创建备份：解锁后在 **新备份密码** 框里输入独立密码生成 `.sfib`，至少两份离线分开放置，密码另存。备份密码不改变当前解锁密码。
- 恢复 `.sfib`：**备份密码** 是单独一个框，填这份 `.sfib` 自己的密码，不是上面的解锁密码；恢复后的便携身份改用该密码解锁。密码没填或填错时窗口直接标红报错并把光标放到该填的框，不会静默停在原样。
- 备份与本机不是同一把身份时不会直接拒绝：先只解密核对（不写盘），弹窗摊开本机指纹与备份指纹让你确认，确认后才替换，并同步改写 `issuer.identity`。替换属于破坏性操作：本机身份已签发的授权立即全部失效，`Build/Keys/` 与 `Build/Trust.props` 要换成新公钥并重新发布客户包。
- 文件丢失或损坏：拒绝签发，要求恢复；没有密码找回后门。

厂商数据位于 **授权工具所在目录的 `IssuerData/`**：`issuer.bin` 为密码加密身份，`issuer.identity` 为指纹，`Issued/` 为历史 `.lic`，`last-product.txt` 为最近产品。请在可写目录运行，换电脑复制整个工具文件夹；更新工具时保留该目录。不要只复制 EXE，不要把它交给客户，也不要在唯一副本上清理 bin/发布目录。旧本机数据仍保留在 `%LOCALAPPDATA%\SoftwareFrame\LicensingIssuer`，不会自动删除。

这是"通用程序＋专属加密数据目录"，本轮没有将身份重新编译嵌入 EXE。仅恢复备份不会恢复历史记录，记录需另外复制 `Issued/`；直接复制完整文件夹会同时带上记录。

便携身份及备份共用 SFIB1：随机 16 字节盐、PBKDF2-HMAC-SHA256 600000 次、AES-256-GCM（随机 12 字节 nonce、16 字节认证标签）。密码或备份全部丢失无法恢复；没有万能密码。若签发身份和所有备份都丢失，只能建立新体系、更新客户程序并重新签发。工具不自动做这种破坏性轮换。

弱密码可能被离线猜解；请使用随机强密码。已控制厂商电脑的程序/管理员仍可能在解锁后访问进程中的凭据，密码加密不是对此类攻击者的保证。全部本地状态被删除也无法可靠判断曾经初始化过，需依赖妥善备份及操作管理。

## 生成客户工具包

在厂商工具填写产品，切到 **客户工具包** 页，点击 **生成客户工具包**，选择空输出目录。自动使用当前签发环境的验证凭据，调用底层发布及审计；支持取消，取消/失败目录不得交付。窗口顶部状态条会先给出信任锚预检结论，不一致时不必等发布失败才知道原因。

**只需要 .NET SDK，不需要 C++ 链接器、MSVC 或 Windows SDK。** 客户包是纯托管交付：早先的 Native AOT 组件已移除，因为它要求机器上装好 Visual Studio 的 C++ 工作负载才能产出原生 DLL，而授权安全并不依赖代码加密（见下文「托管交付与安全边界」）。

客户包内置发行身份和产品，客户无需知道或管理密钥。一个产品的包可用于多台机器，不必逐台构建；不同设备的 `.lic` 仍各自绑定机器码。

发布输出为 Windows x64 自包含 WPF 工具、`Licensing.Client.dll`、`Licensing.Core.dll`、`Licensing.Trust.dll` 及运行时。完整复制目录，不能只复制 EXE。包内不得有厂商工具、签发环境或备份。

底层脚本仍支持受控构建：

```powershell
& 'Software Frame/Licensing/Build/Publish-Client.ps1' -PublicKeyFile 'C:\deployment\public.key' -ProductId 'PackingMachine.ModelA' -OutputDirectory 'C:\deployment\client-win-x64'
& 'Software Frame/Licensing/Build/Test-ProtectedDeployment.ps1' -Directory 'C:\deployment\client-win-x64' -RequireManagedAdapter
```

这里的公钥参数仅供构建自动化，不是客户运行时可选信任配置。校验有两道：格式上只接受 >=2048 位完整 Base64 PKCS#1 DER 公钥，拒绝私钥、PEM、损坏及尾随数据；身份上还必须是 `Build/Trust.props` 钉住的那把指纹，格式合法但不认识的公钥同样被拒。发布目录必须为空，不自动清理用户文件。审计只读：要求 `Licensing.Core.dll`、`Licensing.Trust.dll` 与 `Licensing.Client.dll` 存在，检查隐藏文件、拒绝链接，并拒绝厂商工具、签发身份（`issuer.bin` / `issuer.identity`）、备份（`.sfib`）、调试符号（`.pdb`）、密钥（`.key` / `.pem` / `.pfx` / `.p12`）以及残留的 `Licensing.Native*`。不是完整依赖或防篡改证明。

## 信任锚放在仓库里

公钥是公开数据，因此随仓库提交：`Build/Keys/public-<SHA256>.key` 是验证凭据本体，`Build/Trust.props` 给出它的路径和硬钉指纹。克隆下来直接编译就拿到正确的公钥，不再需要「手工让授权工具和 Trust 对齐」这一步。

- 构建守卫校验的是**身份**，不只是格式：换一个自管公钥去编译会直接失败，除非同时改 `Trust.props` —— 于是信任锚的变更必然出现在 git diff 里，可评审。
- 授权工具解锁签发身份后，状态栏立即给出**发布预检**：本机身份与仓库钉住的指纹是否同一把、`Build/Keys/` 里的公钥文件是否还在。对不上时生成客户包一定会被拒，先在界面讲清楚，不用等完几分钟 `dotnet publish` 才知道原因。
- 换签发身份：新公钥写进 `Build/Keys/`，更新 `Trust.props` 的文件名与指纹，提交，然后重新构建并重新发布所有宿主。
- 临时身份只允许在不交付的构建里用，且必须自己带上指纹：`.local/client.props` 同时写 `LicensePublicKeyFile` 和 `LicenseExpectedPublicKeyFingerprint`（`IssuerFiles.SaveDebugClientConfiguration` 成对写出）。发布脚本的 `-OverrideExpectedFingerprint` 同理，仅用于测试。
- 命令行 `-p:` 是 MSBuild 全局属性，优先于以上两层，发布流程仍由厂商显式掌控。

## 本机开发与 Workbench

1. 在授权工具创建签发身份（或迁移原电脑的本机身份），填写实际产品标识。
2. 需要在本机验证完整激活流程时，直接用 **生成客户工具包** 产出发行包，运行该目录里的激活工具；它和客户拿到的一致，无需额外配置。
3. 使用相同产品给本机机器码签发授权，通过激活工具导入，然后可关闭激活工具。
4. 打开 Workbench。它独立每秒检查；新任务入口仍即时复查，不只信任按钮或缓存。
5. 可签发今天、几秒/几分钟后的明确截止时间，验证非模态提醒、运行中到期、拒绝下一任务。已获准的 10 秒模拟任务完成；关闭宿主只取消自己的模拟任务并释放监控。

`.local/client.props` 只剩下**本机覆盖层**这一层用途：放开发期的产品标识，或临时身份。公钥已由仓库提供，不再需要每个开发者手工准备。三个宿主的身份来源**完全相同**：

| 宿主 | 身份来源 | 换身份后 |
|---|---|---|
| **Workbench** | 编译期嵌入 `Licensing.Trust` | 重建 |
| Debug 版 Activation | 编译期嵌入 `Licensing.Trust` | 重建 |
| Release / 客户包 | 编译期嵌入（构建参数） | 重新发布 |

Workbench 以前会在运行时读 `.local/client.props` 以省去重建，该特例已删除：Workbench 只是体量小的生产宿主，和 MachineApp 走同一条路径。三个宿主一旦来源不同，验证语义就会分叉 —— 开发机上「重启即生效」的通过，并不代表发行包里编译进的是同一把锚。

**任何宿主都不能在运行时读信任配置**：交付客户的程序若允许换公钥，客户只要换成自己的、再用自己签的授权，就能完全绕过 —— 这正是当前设计要防的事。

不要分发 Debug 文件夹。

## 宿主接入边界

**MachineApp 尚未修改，设备未启动。** 激活成功本身不代表生产主程序受到保护。未来 MachineApp 应持有客户端会话，负责业务入口守卫和设备安全；激活工具不需要常驻。

WPF 窗口 Loaded/可见后，在其 Dispatcher 调用 `WpfLicenseSession.Start(owner, trustedPublicKey, productId, onStateChanged, requiredFeature)`。后台默认每分钟检查；Workbench 显式设为每秒。定时器由客户端监控实现，授权核心本身不提供。

- 初始禁止任务；只有即时 `await session.CheckNowAsync(token)` 返回 `Verification.Ok` 且未取消才可进入新任务。
- `Current` 是展示缓存，不是通行证。停止、异常、取消、加载失败均不得放行。
- 状态回调在后台，更新 UI 切到 Dispatcher；保持快速、可取消，不等待长期设备任务或模态弹窗，不在回调内等待释放自身。
- 观察 `Completion`；窗口关闭自动清理，显式释放须在 UI Dispatcher。`ShutdownError`/Trace 可报告退出错误。
- 到期前 30 天每日最多提醒一次，标记持久化，跨重启有效；异常/到期非模态提示，不强杀进程或设备。
- Client 不控制设备。到期怎样禁止新工作、让当前工作安全收尾，必须由生产宿主实现与验收。

## 授权协议与时间策略

- 仅接受 `SF2.Base64Url(payloadJson).Base64Url(signature)`，签名覆盖 `SF2.` 加编码 payload；必需 ProductId，大小写敏感。旧两段授权和缺产品字段的早期 SF2 均不兼容。
- 产品标识 1–64 字符，英数字开头，仅允许 ASCII 英数字、点、下划线、短横线。`SoftwareFrame.Default` 仅保留给底层测试，不可正式签发/发布。期望产品来自可信宿主配置，不能从待导入文件推导。
- V2 机器码来自 Windows MachineGuid 与系统卷序列号，与网卡联网状态无关；重装、换盘、克隆可能改变/复制标识，并非硬件级身份。
- 厂商使用 CreateBound 强制正式产品和 V2 机器绑定；低层 Create 仅供可信调用和测试，不得用来绕过正式流程。
- 客户按 Windows 用户、公钥 DER SHA256 指纹及产品 UTF8 SHA256 指纹隔离：`%LOCALAPPDATA%\SoftwareFrame\Licensing\<公钥指纹>\<产品指纹>\license.lic`。
- 导入先验签再原子替换，无效导入不覆盖旧文件。期限按准确截止时刻 `>=` 判过期；永久授权跳过时间状态。
- 限时授权使用 DPAPI 历史最高时间和排他文件锁，状态丢失/损坏不靠重新导入重置；同一会话还用单调时间检查冻结/减慢，两秒采样容差不随检查累加重置。
- 期限以**天数**签发：到期时刻为今天起第 N 天的 23:59:59（本地时间，签发时转 UTC）。永久授权写 `MaxValue`，跳过一切时间状态。
- 离线交接用 **SFREQ1 申请单**（`.sfreq`，纯文本 `key=value`）：含机器码、产品标识、客户侧生成时间（带时区偏移）、可选的 SFR3 恢复请求。它**不是信任凭据** —— 供应商仍须自行核实客户身份；恢复请求本身由 SFR3 签名保护。读取时产品标识不一致只提示、不自动改，避免签错产品。
- 时间记录不抵御同用户改状态、删除全部状态或磁盘快照回滚。托管程序集可被反编译，无法保证不可破解，也不自动保护宿主的业务判断。

## 时间异常恢复

1. 客户先校正时间，在激活工具点 **时间异常恢复** 生成 SFR3 请求，再点 **导出申请单** 把机器码和这条请求一起存成文件发给厂商。再次生成会使旧请求失效。
2. 厂商核实客户/机器及异常原因，在签发页的可选恢复字段粘贴请求，签发同产品、对应机器的限时授权。
3. 客户导入。签名、产品、机器、期限均通过后，核对并一次性消费本机待恢复请求，重建时间状态及会话单调基准。

错误签名、跨产品/机器、过时请求、重放均拒绝。消费后若写入失败需重新申请，不回滚成可重放请求。恢复时间不得早于恢复授权签发时间；永久授权不需恢复。普通续期应清除保留的 `SoftwareFrame.TimeRecovery` 字段。旧 SFR2 不兼容。

## 托管交付与安全边界

客户包交付的是普通托管程序集（`Licensing.Core.dll`、`Licensing.Client.dll`），**可以被反编译**。这是有意接受的取舍：早先的 Native AOT 方案要求发布机器装好 Visual Studio 的 C++ 工作负载才能链接出原生 DLL，而 AOT 本身也只是提高逆向成本，并不构成安全边界。

真正的安全来自三点，与是否 AOT 无关：

1. **RSA 私钥只存在于厂商的签发身份里**（密码加密的 `issuer.bin`），从不进客户包，因此无法伪造授权。
2. **公钥在编译期嵌入**发行包，客户无法替换成自己的公钥。
3. **机器码绑定 + DPAPI 历史最高时间**，防止一码多用和改系统时间。

反编译者能看到的是「怎么校验」，不是「怎么通过校验」。能绕过的手段是修改宿主程序跳过校验调用 —— 这类攻击 AOT 同样挡不住，只是门槛更高。将来需要提高门槛时，可以在本结构上直接加混淆，不影响模块划分。

`Extension.Core` 仍保留历史公开类型转发及到 Licensing.Core 的引用，不能擅自删 API。本轮没有接入 MachineApp，也不声称生产软件已受保护。
